1. introduction

"lockdown browser" is a funny name for a chromium fork that installs a kernel driver, hooks your keyboard, and then gets upset when you notice. Respondus LockDown Browser 2.1.6.02 is a 64-bit Windows client made of four pieces: a CEF browser, a kernel driver, a user-mode hook module, and a remote exam service. the browser is the part you see. the driver and the hook module are the parts that make the browser feel less like a browser and more like 1984.

2. background

2.1 product architecture

the installed product contains three relevant components:

componentrole
LockDownBrowser.exeCEF browser, policy engine, environment scans, UI, driver client
LockDownBrowser.dllhook module loaded by the main executable; owns global keyboard, mouse, and shell hooks
LockDownService215.syskernel driver; process/image/thread telemetry and a minifilter communication port

the main executable talks to the driver over \ApDriverPort. the driver accepts a client only if the connecting process image matches one of two expected browser paths and passes an Authenticode check. after the handshake, the two sides exchange encrypted messages: process lists, image lists, process records, thread fileless-execution states, and unsolicited process/image notifications.

the hook module is statically imported by the main executable. it exposes four C++-decorated exports: CLDBDoSomeOtherStuff (keyboard only), CLDBDoSomeOtherStuffs (hook-status query), CLDBDoSomeStuff (keyboard + shell + mouse), and CLDBDoYetMoreStuff (mouse reinstall). the driver's minifilter is not a file-system filter in the usual sense; it registers a 0x70-byte FLT_REGISTRATION with no operation-registration array and uses the filter only to host the communication port.

2.2 windows mechanisms in play

the client leans on a fairly small set of documented windows surfaces:

  • input: WH_KEYBOARD_LL, WH_MOUSE, and WH_SHELL hooks installed with a module handle and thread id zero;
  • windows: GetForegroundWindow, SetForegroundWindow, BringWindowToTop, SetWindowPos, and SetFocus;
  • clipboard: AddClipboardFormatListener, OpenClipboard, EmptyClipboard, and SetClipboardData;
  • capture protection: SetWindowDisplayAffinity(hwnd, WDA_MONITOR) and the matching GetWindowDisplayAffinity check;
  • enumeration: OpenProcess, K32EnumProcesses, K32EnumProcessModules, K32GetModuleFileNameExA/W, and version resources;
  • devices: setupapi and WMI against ROOT\CIMV2;
  • services: the wuauserv control path;
  • signatures: WinVerifyTrust and the catalog APIs.

3. methodology

the target was LockDownBrowser.exe 2.1.6.02, 64-bit, image base 0x140000000, SHA-256 starting 86f39c5a.... the driver and hook module came from the same installed copy.

static analysis was mostly ghidra (thank you NSA). three things made it fucking re*****d to work with. first, large parts of the main executable are flattened by MetaFortress, linear disassembly desynchronizes and ghidra function bodies often stop at the first flattened branch. second, the PE parser used by ghidra truncates the .pdata exception directory. reading .pdata directly from the file produced 21,325 usable entries covering 95.9% of .text. third, many string references land in .pdata ranges that were never defined as functions.

the workarounds were mechanical: a one-pass capstone index of RIP-relative string references, a one-pass import-reference index (9,370 call/jump sites, holy moly respondus, compensating for somethin?), a raw .pdata-bounded function summarizer, and a targeted range disassembler for rebuilding obfuscated blocks. when a flattened function still ended early, the block was reconstructed with capstone instead of trusting the decompiler.

4. static analysis

4.1 the driver

the driver creates six singleton objects:

globalobject

DAT_14000f088image monitor
DAT_14000f090thread monitor

the port is \ApDriverPort. the connect callback accepts a PID only when the process image matches one of two \Device\BootDevice-relative browser paths and the image passes Authenticode validation. the accepted PID is stored in the image monitor; everything else gets STATUS_ACCESS_DENIED (0xC0000022).

4.1.1 message protocol

the protocol has a plain form and a secure form. the secure form uses an RSA-2048 OAEP (SHA-256) encrypted 16-byte AES IV followed by AES-256-CBC (PKCS#7) ciphertext. the handshake is:

opcodemeaning
0return the driver's RSA-2048 public key
1import the client's RSA public key
2set the AES-256 session key
3secure envelope; recursively dispatch the inner opcode

queries:

opcodereplybody

0xC-one 0xF0C process record for a PID
0xD0xEPID list
0xF0x10two thread-check states (browser, DWM)
0x110x12smss.exe presence and system boot time
0x13-set a per-connection notification flag
0x140x15verify fileless execution of a TID list

unsolicited notifications go the other way:

opcodebody

4.1.3 monitors

the process monitor seeds itself with ZwQuerySystemInformation(SystemProcessInformation) and then registers PsSetCreateProcessNotifyRoutineEx. on create it builds a 0xF0C record, including the PEB command line via KeStackAttachProcess, version strings, and the owner SID via ZwQuerySecurityObject; on exit it emits the cached record with reason 0.

the thread monitor registers PsSetCreateThreadNotifyRoutine. for browser and DWM PIDs it gets the thread start address with ZwQueryInformationThread(ThreadQuerySetWin32StartAddress), queries the containing region with ZwQueryVirtualMemory(MemoryBasicInformation), and marks unmapped or MZ-less start addresses as fileless code.

the image monitor registers PsSetLoadImageNotifyRoutine and tracks images loaded by the browser and by dwm.exe. each image is recorded as a 0x710 record with signature/owner analysis and sent immediately. the driver also locates smss.exe, checks its presence and startup time, and exposes the system boot time. these are the anti-VM/anti-sandbox signals.

4.3 the main executable

4.3.1 process and module scanning

the central scan is FUN_14022ab00 (0x14022ab00-0x14022d3ce). it runs during initialization and periodically. it deletes the Debugger value under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\utilman.exe, walks a ProcessListPSAPI snapshot, and matches process names and paths against policy lists. the names worth knowing are MiraCast, Spyrix, SelfService.exe, Citrix Workspace, ReadAndWrite.exe, and WUDFHost.exe. it recognizes chrome.exe, msedge.exe, brave.exe, opera.exe, and firefox.exe. ReadAndWrite.exe sets a detection flag at config+0x4bf; Spyrix produces a violation record.

it also enumerates modules loaded in the current process and compares names against allow/block lists. module matches set six flags at config+0x46693-0x46698, later consumed by the VM-allow check. the scan emits the process.list JSON schema and, under config+0x540, calls EnumChildWindows(GetDesktopWindow(), FUN_140242da0, ...).

the process snapshot is built by FUN_14024b1e0. it opens a process with PROCESS_QUERY_INFORMATION|PROCESS_VM_READ, enumerates modules through K32/PSAPI function pointers, reads version resources, and stores the image path. FUN_140239d80 builds the process.list diagnostics payload.

4.3.3 window and desktop enforcement

FUN_1402443d0 is the top-level EnumWindows callback, run every 12 ticks by FUN_1402640c0 while lockdown is active. it hides or closes Office windows (XLMAIN, OpusApp), hides Shell_SecondaryTrayWnd, kills AutoHotkeyGUI, closes Print... and Wireless display toolbar, raises credential dialogs, and closes windows with titles such as Save a..., Select File..., StickyKeys, Sticky Keys, and Power Options.

4.3.4 display, mirroring, and recording

the PnP scan FUN_140231310 enumerates all present devices with SetupDiGetClassDevsW(NULL, NULL, NULL, DIGCF_PRESENT|DIGCF_ALLCLASSES), reads SPDRP_DEVICEDESC, and compares descriptions against a configured device list. FUN_1402319b0 is the mirror-display wrapper used by the scheduler; a nonzero result logs Mirror display detected, closing browser and takes the close/violation path.

the Xbox Game Bar detector FUN_1402373c0 uses SHGetFolderPathA(CSIDL_MYVIDEO) and scans the captures directory; a hit enables capture blocking. a microphone probe (FUN_1402a30a0) opens the default wave input at 22050 hz, 8-bit mono; a WMI function (FUN_140260c50) enumerates camera FriendlyName values, logs Webcam - %s, and checks for virtual.

4.3.5 VM checks

FUN_140268780 builds a string from the six module flags at config+0x46693-0x46698, appending [%d] for each zero flag, and passes it to FUN_1401c2510, a monitor/report routine that builds a request and logs the response. the returned byte is stored at object+0x469ef; when the allow condition holds, the client logs VM allowed - skipping.

FUN_14024a330 reads a VM authorization key from an HKLM registry location. the clear block around 0x14024ae3f calls FUN_1402a17a0, a thin wrapper over RegOpenKeyExA(HKEY_LOCAL_MACHINE, ...), RegQueryValueExA, and RegCloseKey. a successful read is logged as vm key found = %d len = %d key = (%s). the exact key and value names come from the encrypted config string table.

4.3.6 windows update control

FUN_14024c380 queries the wuauserv service with OpenSCManagerW, OpenServiceW, QueryServiceConfigW, and QueryServiceStatusEx. FUN_1402411c0 implements DisableWindowsAutomaticUpdates: it skips D2L sessions, saves the original start type and state, calls FUN_140256ed0(4, 1) to set the service to SERVICE_DISABLED and stop it, and restores the saved configuration on exit.

5. bypass design

5.1 trust-boundary analysis

the driver checks the connecting client's image path and Authenticode signature, and it supplies process/image/thread telemetry. the hook module provides global input hooks. the main executable makes the policy decisions: it interprets driver data, scans the environment, decides when to set display affinity, when to clear the clipboard, when to terminate a blacklisted process, and when to remove the keyboard hooks.

5.2 tool architecture

the tool is small:

  • a 64-bit DLL (FuckLockdown.dll) injected into LockDownBrowser.exe;
  • a native injector (injector.exe) that finds the LOCKDOWNCHROME main-window PID and calls LoadLibraryW remotely;
  • an optional python injector/controller for development;
  • an INI configuration file.

the DLL uses MinHook for x64 API detours, a low-level keyboard hook for hotkeys, and a named event (Local\FuckLockdown_Screenshot) for screenshot triggering. it logs to %TEMP%\FuckLockdown.log.

5.4 focus, clipboard, and termination

focus bypass is the smallest possible lie:

GetForegroundWindow detour
HWND WINAPI DetourGetForegroundWindow() {
    HWND real = pGetForegroundWindow();
    if (!internal && focusBypass && g_ldbMainWnd &&
        real != g_ldbMainWnd && IsWindow(g_ldbMainWnd)) {
        return g_ldbMainWnd;
    }
    return real;
}

the client's attempts to force itself topmost are swallowed:

SetWindowPos detour
BOOL WINAPI DetourSetWindowPos(HWND hwnd, HWND after, int x, int y,
                               int cx, int cy, UINT flags) {
    if (!internal && focusBypass && hwnd == g_ldbMainWnd && after == HWND_TOPMOST)
        return TRUE;
    return pSetWindowPos(hwnd, after, x, y, cx, cy, flags);
}

the tool's own focus operations call the original functions through the MinHook trampolines, so Ctrl+Down can still focus LDB and Ctrl+Up can drop it from the topmost band and cycle to another window.

clipboard preservation is a simple pair of detours:

clipboard detours
BOOL WINAPI DetourEmptyClipboard() {
    if (!internal && clipboardBypass) return TRUE;
    return pEmptyClipboard();
}

HANDLE WINAPI DetourSetClipboardData(UINT fmt, HANDLE mem) {
    if (!internal && clipboardBypass) return mem; // pretend success
    return pSetClipboardData(fmt, mem);
}

the screenshot path uses the original EmptyClipboard and SetClipboardData through raw function pointers, so it can still place a DIB on the clipboard.

termination handling is split on purpose:

TerminateProcess detour
BOOL WINAPI DetourTerminateProcess(HANDLE process, UINT exitCode) {
    const bool self = (process == GetCurrentProcess()) ||
                      (GetProcessId(process) == GetCurrentProcessId());
    if (!internal && terminateBypass && !self) return TRUE;
    return pTerminateProcess(process, exitCode);
}

ExitProcess is always passed through. that distinction matters: the CRT exit wrapper in LockDownBrowser.exe at 0xA7B394 calls GetCurrentProcess and TerminateProcess/ExitProcess, then ends in int3 padding at 0xA7B3C0. if the tool blocks the process's own exit, the wrapper returns into the padding and the client dies with 0x80000003 or 0xC0000409. blocking only other processes preserves the close-blacklisted-apps feature without breaking the client's own shutdown path.

5.5 display-affinity bypass

at injection and once per second, the tool calls the original SetWindowDisplayAffinity(hwnd, WDA_NONE) on every window owned by the LDB process. future SetWindowDisplayAffinity calls on client windows are converted to WDA_NONE, and GetWindowDisplayAffinity returns WDA_MONITOR so PTC 2 remains satisfied:

display-affinity detours
BOOL WINAPI DetourSetWindowDisplayAffinity(HWND hwnd, DWORD affinity) {
    if (!internal && drmBypass && IsCurrentProcessWindow(hwnd)) {
        pSetWindowDisplayAffinity(hwnd, WDA_NONE);
        return TRUE;
    }
    return pSetWindowDisplayAffinity(hwnd, affinity);
}

BOOL WINAPI DetourGetWindowDisplayAffinity(HWND hwnd, DWORD* affinity) {
    if (!internal && drmBypass && IsCurrentProcessWindow(hwnd)) {
        if (affinity) *affinity = WDA_MONITOR;
        return TRUE;
    }
    return pGetWindowDisplayAffinity(hwnd, affinity);
}

this is the key to the DRM screenshot bypass: the real window has no affinity, so BitBlt captures it; the client's integrity check sees the expected WDA_MONITOR value.

5.6 hook-module removal and Win+F1-F12 unlock

the hook module's HHOOKs are read from LockDownBrowser.dll+0x1c000, +0x1c008, and +0x1c010, passed to UnhookWindowsHookEx, and zeroed. the exports CLDBDoSomeOtherStuff, CLDBDoSomeStuff, and CLDBDoYetMoreStuff are patched to xor eax,eax; ret so the main executable cannot reinstall them. the tool's own WH_KEYBOARD_LL hook remains and handles the hotkeys; everything else reaches the system, including Win+F1-F12.

export patching can be disabled with patch_ldb_exports=0; the watchdog still removes any hook that appears, but the client may reinstall between watchdog ticks.

5.8 screenshot pipeline

the screenshot path is native GDI/GDI+:

  1. CreateDCW(L"DISPLAY", ...) obtains the virtual-screen DC;
  2. CreateCompatibleBitmap and BitBlt capture the full screen with SRCCOPY|CAPTUREBLT;
  3. GDI+ encodes the bitmap as PNG to Pictures\FuckLockdown\screenshot_YYYYMMDD_HHMMSS.png, with a fallback to %TEMP%\FuckLockdown;
  4. a DIB copy is placed on the clipboard with the original clipboard functions;
  5. failures are logged, and the PNG encoder/save status is recorded.

the fallback matters. redirected or read-only Pictures folders can fail to produce the target directory even when the process is elevated; using std::filesystem::create_directories and a %TEMP% fallback makes the PNG path reliable.

7. conclusion

LockDown Browser 2.1.6.02 is a layered client: a kernel driver supplies telemetry, a hook module filters input, and the main executable makes policy decisions. the driver's port ACL and image monitoring are meaningful defenses, but they do not protect the user-mode consumer from in-process patching. a relatively small set of API detours inside the signed browser process is enough to suppress focus stealing, preserve the clipboard, block cross-process termination, remove the keyboard hooks, and defeat WDA_MONITOR for screenshots.
